# Plan — issue #107: `several-definitions`, `many-definitions`, and the `checks.rs` split

Fixes github.com/ashbywinch/lucidlint issue #107. Two warn rules replace the
first cut of `large-module`, plus a behaviour-preserving refactor:
`scanner/src/checks.rs` moves three of its rule families into submodules. Every
change ships with Rust unit tests; the three-repo run (this repo, houses,
family-history-album) is the acceptance instrument.

## The gap

`large-function` and `complexity` are function-level. `flat-folder` is
directories. A single file could hold ten rule families — ten concepts — and no
rule said so:

| file | lines | top-level definitions |
|---|---|---|
| `scanner/src/checks.rs` (Rust) | 11,824 | 297 |
| `fix_engine.py` | 7,686 | 264 |
| `lucidlint.py` | 2,774 | 68 |

## The rules: one ladder, two rungs

The signal is the count of top-level **definitions** — functions and classes;
constants are data, not names a reader holds. The two rules are the two rungs of
one ladder, with disjoint ranges so a module never reports both:

| rung | fires on | kind |
|---|---|---|
| strict | 3–10 definitions | `several-definitions` |
| loose | 11+ definitions | `many-definitions` |

The rungs exist so a repo sets its policy: keep both and hold every module to
three, or disable `several-definitions` and hold modules only to eleven. The
ladder is pinned by `the_two_rungs_never_fire_together` (10 → several, 11 →
many, never both).

**The advice follows what the definitions are**, not a second threshold:

- mostly **classes** → each class belongs in a file named after it, so the
  import path states which class lives where;
- mostly **functions** → the functions pass the same data between their
  parameters and no object owns it, so the reader names the domain concepts and
  makes each one a class whose methods they become.

A class with no methods is a value record. "All but one class are records" is one
class plus its value types — one concept in one file — and is exempt. Nested
classes and a class's own methods are not module definitions. Generated modules
(`do not edit`, `generated by`, `@generated` in the opening lines) are exempt.

## What the measurement rejected before the ladder

| criterion | verdict |
|---|---|
| ≥ 800 lines | a line cap: the one-concept long files (album `tools/archive.py` 1,301 lines/9 definitions, `pipeline/api/server.py` 1,332/7, `loft/live/memory.py` 1,153/10) fire for a property they do not have |
| ≥ 800 lines AND ≥ 3 name families / titled sections | the families name vocabulary (`lines`, `box`, `drop`) as often as concepts — a red herring |
| ≥ 25 definitions AND ≥ 3 groups | the count was right; the group condition was the same red herring |
| > 2 classes (class count only) | changed the signal mid-rule: the count of definitions is the ladder, and the class-vs-function distinction belongs in the message |

## The message

Two arms, and each answers the objection it draws:

- **mostly classes** — `'dag/delta_vs_home_node.py' holds 6 top-level
  definitions, 4 of them classes (DeltaVsHome, DeltaVsHomeProvenanceValue,
  DeltaVsHomeValue and one more). A reader looking for one class reads past the
  rest, and the import path never states which class lives where. Turn the
  module into a package — one file per class inside it, each named after its
  class and re-exported from `__init__.py` — so the family keeps its name. A
  class with no methods may stay beside the class that uses it.`

  A family of classes does not scatter across the codebase: it becomes a
  package, which keeps the family's name and gives every class its file. This is
  the answer to `dag/expression.py`'s 12 AST nodes and `loft/live/protocols.py`'s
  protocol registry as much as to a grab-bag.

- **mostly functions** — `'scripts/gen-rules.py' holds 9 top-level
  definitions, 9 of them functions. A free function owns no state, so the data
  the others share arrives as parameters and every call site re-states it. A
  script is not different: the steps it runs build one program state, and no
  name owns it. Name the concept that data belongs to and make it a class: the
  data becomes its fields, and the functions become its methods.`

  The script sentence appears for `scripts/`, `tools/` and `bin/` paths, where
  the objection ("it is a script, functions are fine") actually comes from. The
  arm needs at least three functions to make its claim: "the data the others
  share" is false of one helper, and a class plus two helpers is one concept.

**Framework contracts are an exemption, not a marker.** A decorated top-level
function is registered with a caller outside the module — a router, a CLI, a
test fixture — so it is not a definition the module owns. A module made only of
framework entry points (and records) holds no definitions to name, and is
silent; a module that adds owned functions to its routes reports those and says
`…, and 6 more functions registered with a framework` rather than hiding them
from the count.

## The split

`scanner/src/checks.rs` stays the module root and gains submodules:

- `scanner/src/checks/shared_path.rs` — `PathExpression`, `collect_path_expressions`,
  `shared_path_findings` and the path-shape helpers;
- `scanner/src/checks/duplicate_expression.rs` — `ExpressionOccurrence`,
  `collect_duplicate_expressions`, `duplicate_expression_findings`, the
  expression-key walker and the node floor;
- `scanner/src/checks/review_log.rs` — the §10/§11 families: `duplicate-def`,
  `restating-docstring`, `duplicate-block`, and their statement walkers;
- `scanner/src/checks/module_size.rs` — the two rules and the module shape.

The parent re-exports each public item, so `main.rs` call sites keep reading
`checks::shared_path_findings(...)` and `checks::duplicate_def_findings(...)`.

Moving code out of a file drops that file's `ignore-file` whys, so the two
families the moved code still triggers (`boolean-arg` on the key walker's two
API flags, `complexity`/`large-function` on its exhaustive `Expr` dispatch)
carry their reviewed why into `duplicate_expression.rs`. `duplicate_def_findings`
was covered by `checks.rs`'s file-level `complexity` why; in a 400-line module
that why no longer applies, so it was fixed instead — binding collection became
`bound_names` and the overload-stub test `is_overload_stub`.

Behaviour is unchanged: the same scan run with the pre-split and post-split
binaries reports identical findings on houses and family-history-album (0 added,
0 removed, before counting the new rules), and only line-number shifts plus the
one fixed `complexity` finding differ on this repo.

## Rust

Rust counts the same definitions: top-level `fn`s are functions; `struct`,
`enum`, `trait`, `trait alias`, `type` and `union` are the types; an `impl`
block is not a definition — its methods are the type's, exactly as a class's
methods are the class's; `const`/`static` are data and an inline `mod` is a
container. The record exception reads the same way: a type with no `impl` is a
record.

With no decorator idiom for framework registration, the framework exemption is
Python-only (`#[allow]`/`#[derive]` are on most Rust items, so attributes cannot
mark an entry point).

This repo carries 33 Rust modules; houses and album carry none, so the Rust arm
is measured on one repo only:

| file | definitions | arm | advice |
|---|---|---|---|
| `scanner/src/checks.rs` | 294 (272 functions) | functions | give the shared state an impl |
| `scanner/src/rustscan.rs` | 70 (65 functions) | functions | same |
| `scanner/src/fix.rs` | 51 (40 functions) | functions | same |
| `scanner/src/main.rs` | 48 (36 functions) | functions | same |
| `scanner/radonc/src/visitors.rs` | 9 (5 types) | types | a directory of modules |

16 of the 33 Rust modules fire — including the four files this PR's split just
created (`checks/shared_path.rs` 17, `checks/duplicate_expression.rs` 18,
`checks/review_log.rs` 11, `checks/module_size.rs` 9).

**The advice branches on the rung**, because the two rungs are two different
problems:

- 3–10 functions (`several-definitions`) — one concept with a missing owner:
  *"Name the type those functions operate on and give it an impl — an impl block
  may live in this module. If that type belongs to another crate, put the
  functions behind one trait instead: a foreign type cannot take an inherent
  impl."*
- 11+ functions (`many-definitions`) — a grab-bag: *"Split the module by
  concept: one module per family, each owning the types it introduces. Give a
  family an impl when it has a local type, and keep the free function where a
  `&mut` borrow would conflict."*

Why the loose rung does not say "give it an impl", with the sources:

| source | what it establishes |
|---|---|
| Rust API Guidelines **C-METHOD** | functions with a clear receiver should be methods — true where the receiver is local and unambiguous |
| **The Reference**, implementations | "An implementing type must be defined within the same crate as the original type definition" — a foreign type (`ruff_python_ast::Expr`, `syn::Expr`, `Path`) cannot take an inherent impl, so many of these helpers cannot become methods at all |
| same page | a type may have multiple inherent impls, in any module of the crate — so "an impl" never means one 10k-line impl block |
| **Niko Matsakis, "After NLL: Interprocedural conflicts"** | a `&mut self` method cannot be called while another borrow of `self` is live; the documented workarounds are factoring a sub-struct, free functions over the fields, or view structs |
| **clippy** `too_many_arguments` (7) | group parameters into a new type — the strict rung's advice |
| **clippy** (all 842 lints) | no module- or file-size lint: only `too_many_lines` (100, pedantic, function-level). Rust tooling has no opinion on a 10k-line module, so the judgment is this rule's own |
| **rust-analyzer architecture** | a large Rust codebase deliberately passes an explicit `db` argument to every call rather than threading `self`: free functions over a context are an architecture, not a smell |

Measured receivers explain why the loose rung exists: across the 16 firing Rust
modules no single receiver dominates (`checks.rs`: 272 functions, `&Expr` 60 and
`&ScanState` 50 — 22%). The data is spread across AST types from other crates
and the scan state, so "no object owns it" is true of the module's *concept*,
not of a missing struct.

## Out of scope, deliberately

- **A shared-base exemption** for Python type families — it would spare the AST
  families and protocol registries above. It is a real rule ("classes over one
  base are one family") but it is not this ruling.
- **The split of `checks.rs` itself**: the remaining eleven sections are rounds
  of their own.

## Counting a Rust class equivalent as one definition

Rust has no classes, so counting every free function separately penalised the
language's normal unit: a type plus the functions that operate on it. The Rust
count now groups a module's top-level `fn`s by the type their **first
parameter** takes:

- a function taking one of the module's own types belongs to that type (it is a
  method in exile) — the type and its functions are **one definition**;
- a function taking a foreign type (`&Expr`, `&Path`, `&File`) joins that type's
  group — the helpers around `Expr` are **one definition**;
- a function with no named receiver (`&str`, `&[Stmt]`, `Vec<…>`, or none) is a
  free definition, and is the one the "give it a type" advice is aimed at.

Measured on this repo, the count drops where the class equivalent is real:

| module | before (raw) | after (class equivalent) |
|---|---|---|
| `scanner/src/checks.rs` | 245 | **135** |
| `scanner/src/rustscan.rs` | 70 | **49** |
| `scanner/src/fix.rs` | 51 | **50** |
| `scanner/src/main.rs` | 48 | **45** |
| `scanner/src/checks/record_shape.rs` | 29 | **14** |
| `scanner/src/checks/shared_path.rs` | 17 | **15** |
| `scanner/src/checks/loop_family.rs` | 16 | **8** |
| `scanner/src/checks/duplicate_expression.rs` | 18 | **11** |
| `scanner/src/checks/review_log.rs` | 11 | **7** |

The counting change is right on its own — a type and the functions that take it
are one thing a reader holds — but it does not by itself make the report clean:
the rungs are 3–10 and 11+, so every family module (3–15 concepts) still fires.
The threshold decision is the remaining one, and the numbers for it are below.

## Cleanliness arithmetic (measured 2026-11-16)

Splitting by concept does not converge under the current rungs, and the numbers
say so:

| step | `checks.rs` concepts | ladder findings in this repo |
|---|---|---|
| after the first split (3 sections) | 294 | 23 |
| after `record_shape` (1,002 lines) | 269 | 24 |
| after `loop_family` + `latent_visitor` | 245 | 26 |
| after class-equivalent counting | 135 | 26 |

Every extracted module is still a finding — `record_shape` 14,
`duplicate_expression` 11, `shared_path` 15, `loop_family` 8, `review_log` 7,
`module_size` 10, `latent_visitor` 3 — because a concept family holds 3–15
class equivalents and the ladder flags 3–10 (`several`) and 11+ (`many`). Clean
under the current rungs means every module holds at most **two** definitions,
which no module with three concepts can satisfy.

**Proposed adaptation, for the ruling:**

1. `several-definitions` (3–10) is **Python-only**. Its message is a design
   directive — free functions should become methods — and in Rust the target it
   names (a class) does not exist; three class equivalents in a module is the
   normal unit.
2. `many-definitions` moves to **31+** for both languages. A module holding more
   than thirty class equivalents is a grab-bag by any reading, and the target is
   then reachable: split by concept until each module is ≤ 30.

With class-equivalent counting the remaining Rust findings would be exactly
four — `checks.rs` 135, `rustscan.rs` 49, `fix.rs` 50, `main.rs` 45 — and
`common.rs` (30) is just inside the bar.

With those two changes this repo's ladder findings become six: Rust `checks.rs`
245, `rustscan.rs` 70, `fix.rs` 51, `main.rs` 48; Python `fix_engine.py` 264,
`lucidlint.py` 68. Every other Rust module (≤ 30 after the split) is clean, and
the Python strict rung keeps its "make these methods" directive.
